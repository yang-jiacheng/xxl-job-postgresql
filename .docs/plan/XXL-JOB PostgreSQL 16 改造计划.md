## 1. 目标与范围

将当前 XXL-JOB Admin 从 MySQL 单数据库实现改为 PostgreSQL-only：

- PostgreSQL 16.15。
- 本机目标数据库 `test_db`。
- 固定业务模式 `app`。
- 仅支持全新初始化。
- 不提供 MySQL 存量数据迁移。
- 不保留 MySQL/PostgreSQL 双方言。
- 继续使用原生 MyBatis，不引入 MyBatis-Plus。

Java 模型类型和 `JobScheduleHelper` 的 `SELECT ... FOR UPDATE` 可直接兼容 PostgreSQL，本轮不修改 Java 模型与调度实现。

## 3. 最终实现

### 3.1 PostgreSQL 初始化脚本

文件：`.docs/deploy/tables_xxl_job.sql`。

- 前置条件：`app` 模式已存在，执行用户可在其中创建对象，且不存在同名 XXL-JOB 表。
- 使用单事务和 `SET search_path TO app`。
- 7 个自增主键统一使用 SQL 标准 `GENERATED BY DEFAULT AS IDENTITY`。
- 类型映射：
  - MySQL `int AUTO_INCREMENT` → PostgreSQL `integer GENERATED BY DEFAULT AS IDENTITY`。
  - MySQL `bigint AUTO_INCREMENT` → PostgreSQL `bigint GENERATED BY DEFAULT AS IDENTITY`。
  - `tinyint` → `smallint`。
  - `datetime` → `timestamp without time zone`。
  - `mediumtext` → `text`。
- MySQL `KEY` / `UNIQUE KEY` 已改为 PostgreSQL 普通或唯一索引。
- 保留 4 个日志普通索引，以及日志日报、注册三元组、用户名的唯一性语义。
- 使用 `COMMENT ON TABLE/COLUMN` 保留业务说明。
- 保留原种子数据和固定 ID，并同步 `xxl_job_group`、`xxl_job_info`、`xxl_job_user` identity sequence。
- 未增加外键、检查约束或级联规则。
- 脚本遵循 `.docs/sql-style.md`，为 UTF-8 无 BOM。

### 3.2 MyBatis Mapper

全部 7 个 Mapper 已完成以下改造：

- 删除 MySQL 反引号和失效 MySQL 注释示例。
- 分页统一为 `LIMIT #{pagesize} OFFSET #{offset}`；合法的单参数 limit 保持 `LIMIT #{pagesize}`。
- 页面模糊搜索使用 `ILIKE '%' || 参数 || '%'`。
- 注册超时计算使用 `CAST(#{nowTime} AS timestamp) - #{timeout} * INTERVAL '1 second'`，避免 pgJDBC 未指定类型参数被 PostgreSQL 推断为 interval。
- 注册 upsert 使用三列唯一键上的 `ON CONFLICT ... DO UPDATE`。
- Mapper 中的 SQL 比较符使用 `&lt;` / `&gt;` XML 实体，不使用可读性较差的比较符 CDATA。
- MySQL `!(...)` 改为标准 `NOT (...)`。
- 日志清理子查询改为 PostgreSQL limit 写法并移除多余嵌套。
- 日志聚合 camelCase Map 键使用双引号别名。
- 6 个自增 ID insert 保留 `useGeneratedKeys="true"` 和 `keyProperty="id"`，增加 `keyColumn="id"`。

### 3.3 依赖

`pom.xml` 当前最终事实：

- Spring Boot 3.5.7。
- Druid Spring Boot 3 Starter 1.2.24。
- MyBatis Spring Boot Starter 3.0.4。
- pgJDBC 42.7.13，compile scope。
- Guava 33.5.0-jre，compile scope。
- MySQL Connector/J 已移除。

pgJDBC 和 Guava 由项目属性显式管理。这是用户后续调整后的最终依赖口径，不再采用旧方案中的“pgJDBC 完全交由 Spring Boot BOM 管理”。

Guava 是针对启动日志中的 `NoClassDefFoundError: com/google/common/collect/Lists` 补充的直接依赖。当前代码已加入，但尚无用户补充依赖后的新启动日志，不能声明运行时问题已经验证解决。

### 3.4 数据源

`src/main/resources/application.properties` 当前实现：

- Druid db-type 为 `postgresql`。
- 驱动为 `org.postgresql.Driver`。
- URL、用户名和密码使用环境变量，并提供本机默认值。
- 默认 JDBC URL 包含 `currentSchema=app`。
- Druid `connection-init-sqls=SET search_path TO app` 当前被注释。
- validation query 为 `SELECT 1`。
- Druid `stat,slf4j` 过滤器启用。
- `ACCESS_TOKEN` 仍为必须提供的环境变量。

当前 schema 选择以 JDBC URL 的 `currentSchema=app` 为准。文档不得记录 application.properties 中的数据库密码默认值。

### 3.5 Docker 部署说明

`.docs/deploy/xxljob-docker/README.md` 已将示例 URL 改为 PostgreSQL，并说明初始化脚本、`app` 模式和权限要求。

当前存在一个需要后续统一的部署细节：Docker 示例 `DB_URL` 没有 `currentSchema=app`，README 仍描述 Druid 会执行 `SET search_path TO app`，但 application.properties 中对应 connection-init-sqls 已被注释。若实际使用 Docker，应在以下策略中择一并同步文档：

1. Docker JDBC URL 增加 `?currentSchema=app`；或
2. 重新启用 Druid `connection-init-sqls=SET search_path TO app`。

## 6. 启动日志诊断记录

证据文件：`D:/java/logs/xxl-job-admin/xxl-job-admin-2026-09-05.0.log`。

- 第一次启动失败：未提供 `ACCESS_TOKEN`，Spring 无法解析占位符。
- 第二次启动：Web 容器和 XXL-JOB Admin 已启动，但后台线程在 Druid PostgreSQL 解析器中因缺少 `com.google.common.collect.Lists` 失败。
- 根因：Druid 1.2.24 运行时调用 Guava，但其发布依赖没有把 Guava 传递到应用运行类路径。
- 当前处理：用户已在 POM 中加入 Guava 33.5.0-jre compile 依赖。
- 后续日志片段已经执行到 PostgreSQL 注册查询，但没有完整重启日志，不能据此声明所有运行流程已通过。
- 后续 Registry 故障：`findDead` 的 `? - ? * INTERVAL '1 second'` 因 pgJDBC 将普通 `Timestamp` 作为未指定类型参数绑定，被 PostgreSQL 将内部表达式推断为 interval，最终形成非法的 `timestamp without time zone < interval` 比较。
- 当前处理：`findDead` 与同构的 `findAll` 均改为 `CAST(#{nowTime} AS timestamp) - #{timeout} * INTERVAL '1 second'`；`timestamp` 等价于 `timestamp without time zone`。
- 横向检查：其他 Mapper 没有绑定时间参数参与 interval 运算；3 个 Mapper 中共 10 处比较符 CDATA 已替换为 XML 实体。
- 验证状态：代码已通过 XML 解析和静态残留扫描，运行结果等待用户自行重启验证；Agent 未执行 SQL 或启动应用。
- 构建输出状态：日志加载的 `target/classes/mybatis-mapper/XxlJobRegistryMapper.xml` 仍是旧副本。Agent 按项目规则未执行 Maven 编译，也未修改构建产物；用户重启前需由 IDE 或构建工具刷新资源。
