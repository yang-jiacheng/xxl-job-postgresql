### 3.3 初始化脚本的改造前基线与当前结果

改造前，`.docs/deploy/tables_xxl_job.sql` 是 v2.4.1 的 MySQL DDL：

- 8 张表：`xxl_job_info`、`xxl_job_log`、`xxl_job_log_report`、`xxl_job_logglue`、`xxl_job_registry`、`xxl_job_group`、`xxl_job_user`、`xxl_job_lock`。
- 7 个 `AUTO_INCREMENT` 主键。
- MySQL 专有的反引号、`SET NAMES`、`ENGINE=InnoDB`、`COMMENT` 列语法、`KEY` / `UNIQUE KEY`、`tinyint`、`datetime` 和 `mediumtext`。
- v2.4.1 索引语义是 3 个普通二级索引（日志 2 个、Registry 三元组 1 个）和 2 个唯一索引（日报日期、用户名）。
- Registry 三元组在 v2.4.1 中是普通索引，不是唯一索引。
- 种子数据只有 1 个执行器组、1 个示例任务、1 个管理员用户和 1 条调度锁。

当前脚本已按同一 v2.4.1 基线改为 PostgreSQL 16：保留 8 表和原始列顺序，使用 7 个 identity、8 个具名主键、3 个普通索引、2 个唯一索引、原始 4 类种子及 3 次 sequence 同步；11 个原 `datetime` 列使用 `timestamp` 简写，固定时间种子使用显式 `TIMESTAMP` 字面量。PostgreSQL 元数据会将该简写显示为 `timestamp without time zone`，时间语义未改变。

### 3.4 Mapper 与 Java 契约

改造前 7 个 Mapper 的不兼容或语义不等价点如下；表中问题当前均已修复：

| 文件 | 改造前问题 |
| --- | --- |
| `XxlJobGroupMapper.xml` | 反引号、MySQL 逗号分页、MySQL 默认大小写不敏感搜索语义 |
| `XxlJobInfoMapper.xml` | 逗号分页、模糊搜索、失效的 `LAST_INSERT_ID` 注释 |
| `XxlJobUserMapper.xml` | 逗号分页、用户名模糊搜索 |
| `XxlJobLogMapper.xml` | 逗号分页、反引号、`!(...)`、清理子查询中的 MySQL limit、未加双引号的 camelCase 聚合别名 |
| `XxlJobLogGlueMapper.xml` | 反引号、清理子查询中的 MySQL limit、`LAST_INSERT_ID` 注释 |
| `XxlJobLogReportMapper.xml` | 反引号、`LAST_INSERT_ID` 注释 |
| `XxlJobRegistryMapper.xml` | 两处 `DATE_ADD(... INTERVAL ... SECOND)`、反引号 |

需要保留的 v2.4.1 Java 契约：

- `JobRegistryHelper` 调用 `registryUpdate`，未命中时再调用 `registrySave`；`XxlJobRegistryDao` 也只暴露这两个方法。当前分支不应直接替换成 v3.1.0 的 `registrySaveOrUpdate`。
- `JobScheduleHelper` 使用手写 JDBC 对 `xxl_job_lock` 执行 `SELECT ... FOR UPDATE`；PostgreSQL 支持该语法，但连接必须实际进入 `app` 模式。
- `JobLogReportHelper` 读取 `triggerDayCount`、`triggerDayCountRunning`、`triggerDayCountSuc`，PostgreSQL 中 Mapper 必须用双引号保留这些 camelCase 别名。
- 6 个写入自增 ID 的 Mapper insert 使用 `useGeneratedKeys`；PostgreSQL 改造时应补充 `keyColumn="id"`。
- 当前模型的 `int`、`long`、`String`、`java.util.Date` 可映射到计划中的 PostgreSQL 类型，预期无需修改模型类。

## 4. 数据库只读验证事实

2026-09-05 初始化前通过 PostgreSQL MCP 执行只读元数据查询，结果如下：

| 项目 | 事实 |
| --- | --- |
| 服务版本 | PostgreSQL 16.15，64 位 |
| 当前数据库 | `test_db` |
| 业务模式 | `app` 已存在，owner 为 `app_owner` |
| 当前连接权限 | 对 `app` 具有 USAGE 和 CREATE |
| 当前 MCP 会话 search_path | `"$user", public`，current_schema 为 `public` |
| `app` 当前对象 | 只有与 XXL-JOB 无关的 `test_tb` |
| `xxl_job_*` 对象 | `app` 与 `public` 中均不存在 |

结论：

- 数据库满足“全新初始化”的前提，不存在需要迁移或清理的 XXL-JOB 表。
- `app.test_tb` 不属于本次范围，必须保留。
- MCP 会话的 search_path 不代表应用最终连接；应用能否进入 `app` 取决于运行时实际 `DB_URL` 是否保留 `currentSchema=app`。
- 本轮未执行 DDL、DML、应用启动或测试。后续仍只允许 Agent 做只读数据库查询，DDL 由用户执行。

用户执行初始化脚本后，Agent 再次只读核验：`app` 中存在全部 8 张 XXL-JOB 表和 69 列，`public` 未出现同名表；列顺序、类型、长度、可空性、默认值和 identity 与脚本 69/69 一致；8 个主键、3 个普通索引、2 个唯一索引、4 类种子均正确；group/info/user 三个种子 sequence 均为 `last_value = 1`、`is_called = true`，下一值不会与固定 ID 1 冲突；`app.test_tb` 仍存在。

| 维度 | 官方 2.4.1 | 官方 3.1.0 | 对当前改造的影响 |
| --- | --- | --- | --- |
| Java | 8 | 17 | 当前保持 Java 8 |

| MyBatis starter | 2.3.2 | 3.0.4 | 当前保持 2.3.2 |

官方 v3.0.0 说明数据模型和通信协议对 v2.4.* 向前兼容，但这不等于代码、依赖和 SQL 可直接互换。v3.1.0 还加入 AI 执行器、固定速度调度修复、Cron 前端兼容、RollingLog 权限/XSS、Glue IDE 与依赖升级；这些均不属于当前 PostgreSQL 方言改造范围。

### 5.2 数据库与 Registry 差异

| 维度 | 2.4.1 | 3.1.0 |
| --- | --- | --- |
| 表数量 | 8 | 8 |
| 日志普通索引 | `trigger_time`、`handle_code` | 额外增加 `(job_id, job_group)`、`job_id` |
| Registry 三元组 | 普通索引 | 唯一索引 |
| Registry 写入 | Java 先 UPDATE，未命中再 INSERT | 单方法 `ON DUPLICATE KEY UPDATE` |
| 种子执行器组 / 任务 | 1 / 1 | 2 / 3，增加 AI 示例 |

上述 Registry 和日志索引变化来自 2.5.0 之后的上游优化，不是 PostgreSQL 语法转换的必要条件。当前计划以 2.4.1 源码契约为准：保留普通 Registry 索引和 update-then-insert，不引入 `ON CONFLICT` 或 v3.1.0 Java 接口；若未来要吸收并发注册优化，应作为独立功能升级。

### 5.3 可复用与不可照搬的 v3.1.0 改造经验

可复用：

- MySQL 类型到 PostgreSQL 类型的映射、identity 主键、`COMMENT ON`、固定 ID 种子后的 sequence 同步。
- Mapper 的 `LIMIT ... OFFSET ...`、`ILIKE`、反引号清理、`NOT (...)`、清理子查询改写。
- generated keys 增加 `keyColumn="id"`。
- Registry 时间计算对 `nowTime` 显式 `CAST(... AS timestamp)`，避免 pgJDBC 参数类型推断错误，并与 DDL 和现有 `java.util.Date` 映射保持一致；该写法仍是无时区 timestamp。
- 聚合 Map 的 camelCase 别名使用 PostgreSQL 双引号。
- JDBC URL 使用 `currentSchema=app`。

不可照搬：

- Java 21、Spring Boot 3、Druid Boot 3 starter、Druid 1.2.24、MyBatis 3.0.4。
- 针对 Druid 1.2.24 运行日志补充的 Guava 依赖；当前 Druid 1.1.24 没有同一条已验证故障证据。
- v3.1.0 的 Registry 唯一索引、`registrySaveOrUpdate` 与 `ON CONFLICT`。
- v3.1.0 的 4 个日志索引、2 个执行器组和 3 个任务种子。
- v3.1.0 的调度、Controller、认证、前端和安全修复代码。

## 6. 当前改造边界

1. 只改数据库适配直接相关的 POM、数据源、DDL、7 个 Mapper 和 Docker 说明。
2. 默认不修改 Java 业务代码、DAO 接口、模型、Controller 或前端。
3. PostgreSQL DDL 严格以 v2.4.1 的 8 表、索引和种子语义为基线。
4. 使用 `GENERATED BY DEFAULT AS IDENTITY`，便于插入固定种子 ID，并同步实际写入种子的 3 个 sequence。
5. schema 策略以 JDBC `currentSchema=app` 为主；Docker 示例必须同步，不能依赖当前被注释的 connection-init-sqls。
6. 不新增外键、检查约束、级联规则或上游 2.5+/3.x 的性能索引。
7. 遵循 `.docs/sql-style.md`，文件使用 UTF-8 无 BOM 和普通 ASCII 标点。
8. 按项目规则不运行 Maven 编译；使用 XML/POM 解析、静态扫描和用户执行后的只读数据库元数据完成验证。

## 7. 关键风险

1. **配置需持续联动**：properties、POM、Mapper 与 DDL 当前已对齐；后续若单独修改其中一处，必须重新执行一致性检查。
2. **Registry 版本错配**：把 v3.1.0 upsert 复制到 v2.4.1 会同时要求唯一索引、DAO 和 Helper 改动，超出纯方言改造。
3. **聚合别名折叠**：未加双引号的 camelCase 别名会被 PostgreSQL 转为小写，导致 `JobLogReportHelper` 取值失败。
4. **时间参数推断**：Registry 的 interval 表达式必须显式转换 `nowTime`。
5. **identity sequence**：固定 ID 种子写入后不自动推进 sequence，必须同步 group、info、user 的 sequence。
6. **schema 漂移**：运行时覆盖 `DB_URL` 时若遗漏 `currentSchema=app`，SQL 会落到 `public` 查找。
7. **敏感默认值**：当前 properties 含本地敏感默认值，文档和外部工具输出不得传播。
